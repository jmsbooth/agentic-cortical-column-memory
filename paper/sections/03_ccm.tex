\section{CCM architecture}

\subsection{Agent-internal architecture}

The canonical relationship is shown in Figure~\ref{fig:ccm-architecture}. A CCM column is not an agent. An agent contains its reasoning model, instructions, planning, tools, working context, and optionally one CCM instance composed of multiple bounded columns. CCM returns bounded memory context to the reasoning model; it does not replace the agent's reasoning loop.

The default conceptual mode is shared-model: all columns may call the same parent-agent model while maintaining distinct local state. A provider-neutral adapter also permits heterogeneous models. The architecture is independently usable by a single agent and does not require a multi-agent orchestrator or TPAA.

\subsection{Reference frames}

A CCM reference frame answers: relative to what structured context does an observation have meaning? Formally,
\[
  F=(f,k,o,s,T,O),
\]
where $f$ is a stable identity, $k$ is a frame class, $o$ is the origin, $s$ is the current state, $T$ is a set of validated transitions, and $O$ maps locations to observation identifiers. A transition $(a,s_i,s_j)\in T$ is valid only when the current state is $s_i$; an observation is attachable only when its frame and location are valid.

Frames may be object-, actor-, process-, temporal-, spatial-, relational-, workflow-, or ontology-relative. They are not necessarily spatial and are not agent personas. A frame can organize a mug's object-local handle location, an incident's authorization workflow, or a temporal assignment history.

\subsection{Columns}

A column is a bounded persistent modeling unit responsible for one coherent subset or perspective of world state. It may accept observations, place them in a frame, maintain local state and relations, retain temporal history, track conflicting observations, derive hypotheses, identify missing information, and emit a bounded external representation. It need not independently operate as a full autonomous agent.

The inspectable interface is:

\begin{verbatim}
observe(observation)
update_hypotheses(candidates)
propose_action(available_actions)
emit_state()
receive_peer_state(peer_state)
vote()                 # optional reconciliation algorithm
commit(status)
\end{verbatim}

The interface separates local update from communication. Peer state is serializable and bounded; hidden reasoning is not exchanged. A column can contribute to committed, abstained, unresolved, or complementary state.

\subsection{Memory model}

CCM distinguishes immutable historical observations from current interpreted state. The principal object classes are Observation, Relation, State, Hypothesis, Transition, and Prediction. An observation contains stable identity, content, frame and location, source, provenance, sequence, confidence, validation state, observed time, recorded time, validity interval, optional supersession, and relations. A Relation is a typed subject--predicate--object assertion with its own provenance and validity. State is derived and replaceable; history is not.

For example, an incident frame can contain the actor, session, device, credential, resource, action, time, and authorization context. The ontology, if supplied, defines valid entity and predicate types. CCM stores instances: ``Session S19 accessed Resource R4 at 14:32 using Token T7.'' A provenance-bearing recall can return the relevant state and source observation without exposing unrelated history.

\subsection{Recall and context assembly}

The agent-facing interface is:

\begin{verbatim}
recall(query, current_context, budget)
\end{verbatim}

The result contains relevant observations, current state, supporting IDs, temporal context, provenance, unresolved conflicts, hypotheses, confidence, and an auditable token count. Context assembly converts that result into bounded model input. The experimental harness measures recall precision, recall, provenance coverage, relevant-context density, context tokens, candidate count, retrieval latency, and update cost. CCM does not assume that raw memory is copied into the prompt.

\subsection{Reconciliation rather than voting}

Local states may be compatible, complementary, contradictory, unresolved, or unknown. The reconciliation operation classifies these outcomes without forcing a winner. Structured quorum voting is retained as one optional algorithm for a downstream decision. It is not required for every recall and is not the defining mechanism of CCM.

\subsection{Active evidence}

When recalled state is incomplete or contradictory, a column may identify a missing observation and an optional policy may select an available action by expected information gain per cost. The returned observation is validated, appended with source and provenance, and included in the next recall. An action cannot create evidence without an environment response.

\subsection{Primary algorithm}

Algorithm~\ref{alg:ccm} is implementation-independent pseudocode. It makes recall, reconciliation, temporal history, and disagreement explicit.

\begin{enumerate}
  \item Initialize an agent's bounded columns, reference frames, append-only memory, and run manifest.
  \item Accept externally returned observations with source, provenance, sequence, and temporal metadata.
  \item Recall a bounded context for the agent query; assemble only the required context for the reasoning model.
  \item Each column updates local state and hypotheses, then emits a bounded structured state.
  \item Reconcile emitted states as agreement, complementary, contradiction, unresolved, or unknown.
  \item Optionally apply a structured quorum or another decision rule; never convert a hypothesis into an observation.
  \item If uncertainty remains and budget permits, select and execute one evidence action, append its result, and repeat.
  \item Otherwise return the bounded state with provenance and an explicit outcome.
\end{enumerate}

\subsection{Invariants}

The implementation and tests enforce: observations are immutable and provenance-bearing; hypotheses cannot masquerade as observations; current state never deletes history; temporal validity and supersession are explicit; columns do not silently mutate one another; contradictory and unknown outcomes remain visible; recall output is bounded and provenance-linked; and manifests record configuration, model/task versions, seed, hardware, resources, and Git commit.
